## Backend tests and coverage (decided 2026-10-17)
- **Runner:** backend unit tests use Node's built-in test runner (`node:test` + `node:assert/strict`). It is part of Node itself, so no test framework is added. The rules booklet lists pytest/JUnit/TestNG only as examples ("such as"), and no penalty in `Docs/spec/19` covers the choice of test tool.
- **Location:** test files live in the root `tests/` folder, as the spec requires, named `*.test.js`. They import backend code by relative path (for example `../backend/src/...`).
- **How `run_tests.sh` runs them:** it uses `node --test --experimental-test-coverage`. When the host has no Node, it runs the same command inside `node:20-alpine` through Docker. If `backend/node_modules` is missing, it runs `npm ci --prefix backend` first.
- **TypeScript:** Node 20 can't run `.ts` files directly. If the backend is written in TypeScript, the tests need a loader.
- **`COVERAGE.json`:** it declares line coverage for six areas: `fixtures`, `scoring`, `standings`, `store`, `roster`, `rbac`. Judges may run `./run_tests.sh`, and an area's bonus is voided if the measured figure is more than 2 percentage points below the declared one.
  - Take each figure from the coverage table, using only that area's backend source files. The table also lists the test files themselves; exclude them.
  - Never raise a figure without measuring it.
- Mobile Jest tests are separate and are not part of `COVERAGE.json` or `run_tests.sh`.

## Architecture (big picture)

### Two API surfaces on one backend (host port 8080)
- **`/audit/v1/*` and `/health`**: the grader contract. Field names, types, status codes and error codes are compared literally. No auth, except the 7 RBAC probe routes (`Docs/spec/15`). Never rate-limited (the grader may send 200 req/s).
- **`/api/v1/*`**: routes the mobile app calls. Only `/api/v1/ping` is in the spec; the rest are **PROPOSED** in `mobile/architecture/07-networking-and-api.md`. They are JWT-authenticated and rate-limited (100 requests per rolling 10 s per client IP, 429 with `Retry-After`). They must be thin wrappers over the same services as the audit routes. `/api/v1/offline-sync` in particular must run the identical code path as `/audit/v1/offline-sync`.

### Rules every endpoint shares (`Docs/spec/04`)
- Validation order: 400 (schema) → 404 (unknown id) → 409/402 (business rule). The first failing step wins. On RBAC probes, authorization (401/403) is checked before anything else, and cross-tenant access by a non-super-admin is 403, never 404.
- Every non-2xx response body is `{"error":{"code","message","details":{}}}`, and `details` is always an object.
- Idempotency: replaying a request with the same client id (`event_id`, `order_id`, `request_id`, `action_id`) and an identical body returns the stored result with 200 and changes nothing.
- Ids are stored and returned verbatim. Timestamps use `YYYY-MM-DDTHH:MM:SSZ`. Money is integer paisa with currency `"PKR"`.
- Limits: 5 s per request (10 s for reset), and bodies over 1 MB get 413.

### Event-sourced scoring → standings
Each match is an append-only event stream (`Docs/spec/11`). League fixtures create streams automatically; stand-alone matches start with `match_init`. Match status, score, wickets and balls are all derived from the active (non-compensated) events, and per-model limits come from the sport config. A `compensation` appends a new signed event that neutralises an earlier one; existing rows are never modified. Standings (`Docs/spec/12`) are computed from the same logs using the league's points and `tie_break_order`. The final `draw_lots` tie-break is seeded by `lots_seed`, which defaults to the last reset's `seed`.

### Signatures (`Docs/spec/06`)
The signature is `HMAC-SHA256(DAY1_SALT, id + "|" + canonical_json(payload))` in lowercase hex. It goes on every event (in `/events`, `/score` and offline-sync results) and on every checkout receipt. Canonical JSON means recursively sorted keys, no whitespace, non-ASCII left unescaped, and integers without `.0`. The spec gives a Python reference implementation and test vectors; check any Node port against vector 1.

### Reset, seed and health (`Docs/spec/07`)
`POST /audit/v1/reset` wipes all state and recreates the exact baseline: tenants, store, RBAC scenario ids, demo users and the 4 sports. Two resets in a row must leave identical state, and the grader calls it before each test group. `/health` returns 200 only when the database is reachable **and** the baseline is seeded. The five demo accounts (listed in `README.md`) must exist after every startup and every reset.

### Grading environment (`Docs/spec/03` + `Docs/rules-booklet.md` §3)
The two documents describe different grader machines:

| | Spec | Booklet |
| --- | --- | --- |
| Machine | Ubuntu 22.04, 4 vCPU, 8 GB RAM, Docker 24+ with Compose v2 | GitHub Actions cloud runner, `ubuntu-latest`, 16 GB RAM |

Design for the smaller machine.
- `up -d --build`, including image pulls, must finish within 10 min, and `/health` must return 200 within 120 s after that.
- Internet is available only during the build. Running services must not download anything, so bake every binary into the image at build time.
- No manual steps and no pre-created volumes.
- Approved infra: PostgreSQL 16, Redis 7, MinIO, RabbitMQ (the `queue` service). The PDF receipt engine must come from the approved list (WeasyPrint, wkhtmltopdf, Puppeteer) or be a PDF library.

### Mobile (`mobile/architecture/01`)
The app is built from screens, one `use<Screen>Screen()` hook per screen, and offline-first repositories.
- SQLite (expo-sqlite + Drizzle) is the single source of truth for cached data. Screens read it through `useLiveQuery`, and network refreshes write into it.
- Scoring and roster actions are queued in SQLite while offline. They sync through `/api/v1/offline-sync` using the exact action format in `Docs/spec/16`.
- The JWT is stored only in `expo-secure-store`.
- The app never computes signatures or sees `DAY1_SALT`, and checkout works online only.
- Campus Wi-Fi isolates devices from each other, so phone ↔ laptop testing runs over the team's phone hotspot. Gradle dependencies must be cached before the first build on campus.
